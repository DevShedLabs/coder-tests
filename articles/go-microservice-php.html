Go for Long-Running Processes, Called From PHP

✍️ Jeffrey 📅 Aug 10, 2026 ⏱ 8 min read

PHP is an old friend. It starts, does its job, and exits — usually in milliseconds. That lifecycle is what makes it so reliable for web requests. But it's also a limitation. Some tasks aren't finished in a single request. Some jobs need to keep running — polling a queue, processing files, waiting for a WebSocket connection — long after PHP has packed up and gone home.

That's where Go steps in. We already established that Go makes a great friend. Now let's give it a job: run a long-lived process, and let PHP knock on its door whenever something needs doing.

Why a Long-Running Process Can't Live in PHP

Every PHP request is effectively born and dies in the time it takes to render one page. There's no persistent memory between requests by default, and holding a request open for minutes just to keep a worker alive is a recipe for timeouts, exhausted connections, and grumpy users.

Meanwhile, Go is built for exactly this:

  • It keeps running. A Go server boots once and stays up for months.
  • It handles concurrency. Goroutines juggle thousands of tasks cheaply.
  • It's fast. Compiled and near-instant startup, no interpreter overhead.
  • It's memory-aware. You can hold state, caches, and connections in one place.

The Architecture: A Go Microservice

Instead of asking PHP to babysit a long job, we run a standalone Go service. PHP calls it over HTTP. The Go service absorbs the long-running work, and PHP gets on with answering requests. They never have to care about each other's internal lives.

Step Who What happens
1 PHP A user submits a heavy job to your web app.
2 PHP → Go PHP sends the job to your Go microservice via HTTP.
3 Go Go starts the long task and returns a job ID immediately.
4 PHP PHP replies to the user right away — no blocking wait.
5 Go Go keeps processing while the web keeps breathing.

A Minimal Go Service

Here's a tiny example. The Go service accepts a job, kicks it off in the background, and answers immediately. No waiting around. 

Go — microservice.gopackage main

import (
    "encoding/json"
    "fmt"
    "log"
    "net/http"
    "time"
)

type Job struct {
    ID   string `json:"id"`
    Data string `json:"data"`
}

var results = make(map[string]string)

// simulate a long-running task in a goroutine
func process(job Job) {
    time.Sleep(10 * time.Second) // pretend this is real work
    results[job.ID] = "done with: " + job.Data
}

func submitHandler(w http.ResponseWriter, r *http.Request) {
    var job Job
    if err := json.NewDecoder(r.Body).Decode(&job); err != nil {
        http.Error(w, err.Error(), http.StatusBadRequest)
        return
    }
    job.ID = fmt.Sprintf("job-%d", time.Now().UnixNano())
    go process(job) // returns immediately

    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(map[string]string{"job_id": job.ID})
}

func statusHandler(w http.ResponseWriter, r *http.Request) {
    id := r.URL.Query().Get("id")
    result, ok := results[id]
    if !ok {
        http.Error(w, "not done yet", http.StatusAccepted)
        return
    }
    json.NewEncoder(w).Encode(map[string]string{"status": result})
}

func main() {
    http.HandleFunc("/submit", submitHandler)
    http.HandleFunc("/status", statusHandler)
    log.Println("Go microservice listening on :8080")
    log.Fatal(http.ListenAndServe(":8080", nil))
}

Notice the go process(job) line. That single keyword spins the task off into a goroutine so the service can serve the next request immediately. Ten seconds of work happens while PHP keeps talking to users.

Calling It From PHP

Now the fun part. PHP just makes HTTP calls using cURL — something it's done happily for a decade. Two calls: one to submit the work, and one to check the status. 

PHP — submit.php<?php

function go_submit(string $data): string {
    $ch = curl_init('http://localhost:8080/submit');

    curl_setopt($ch, CURLOPT_RETURNTRANSFER, true);
    curl_setopt($ch, CURLOPT_POST, true);
    curl_setopt($ch, CURLOPT_HTTPHEADER, ['Content-Type: application/json']);
    curl_setopt($ch, CURLOPT_POSTFIELDS, json_encode(['data' => $data]));

    $out = curl_exec($ch);
    curl_close($ch);

    $decoded = json_decode($out, true);
    return $decoded['job_id'] ?? '';
}

function go_status(string $jobId): ?string {
    $ch = curl_init('http://localhost:8080/status?id=' . urlencode($jobId));

    curl_setopt($ch, CURLOPT_RETURNTRANSFER, true);
    $out = curl_exec($ch);
    curl_close($ch);

    return json_decode($out, true)['status'] ?? null;
}

And that's it. `go_submit()` fires the job and gets back an ID almost instantly. `go_status()` polls for the result. Both PHP functions stay fast because the heavy lifting lives in the Go process, not in the web thread.

Wiring It Into a Page

A typical flow in your PHP app looks like this: 

PHP — handle_request.php<?php

$upload = $_POST['file_to_process'] ?? '';

// Hand off the long job to Go, get an ID fast.
$jobId = go_submit($upload);

// Show a "processing…" screen while Go does the work.
echo "Your job is queued! ID: {$jobId}";

// Later, poll for the result:
// $status = go_status($jobId);
The user sees an instant response. The long task runs safely in its own process. PHP stays snappy. Go stays busy. Everyone wins.

Operational Notes for the Real World

A toy example is nice, but a friendly microservice in production deserves a little more care:

  • Run it separately. Use a systemd service, Docker container, or supervisor so Go restarts if it crashes.
  • Persist state. If you need results to survive a restart, back them up to a database instead of an in-memory map.
  • Secure it. Bind Go to localhost or a private network so only your PHP app can reach it — or protect the endpoint with a shared token.
  • Add timeouts. Set reasonable cURL timeouts in PHP and cancel long goroutines that are no longer needed.
  • Scale horizontally. Because PHP and Go communicate over plain HTTP, you can run many Go workers behind a load balancer when demand grows.
Prefer something even lighter? If your job is truly background-only, PHP can enqueue it into a message queue (like Redis or RabbitMQ) and a Go worker can consume from the other side. The HTTP microservice is the simplest jumping-off point, but the same friendship scales down — or up — to whatever fits.

Friends in Different Time Zones

PHP and Go don't live in the same process, and that's exactly the point. Each runs on the schedule and in the environment it's built for. Go stays awake for the long haul; PHP answers each visitor cheerfully and moves on. Split responsibilities, no jealousy, no arguments.

That, right there, is what it means for two languages to be friends: let the one that thrives on endurance handle the long-running work, and let the one that thrives on quick hellos handle the front door.
